Cinatra — Application Design — Artifacts

/artifacts is the library — everything the acting user's agents and uploads have produced, opened by each row's effective identity. Object administration lives on its own admin-gated page, /configuration/objects, and targeted restore has its own route. Part of Cinatra Application Design; match it exactly.

Version 0.4.0

I. Two surfaces — the library and the object console

/artifacts library · /configuration/objects admin

/artifacts is the library, and nothing else. It lists exactly the acting user's artifacts, for every user — there is no mode toggle and no Library button, because the library is the lone view. The page opens with the standard page header (title Artifacts, a one-line description, a closing etched rule), then a toolbar over the list. The sidebar entry is unchanged. Object administration is not a mode of this page; it moved out entirely (§VIII).

Object administration lives at /configuration/objects. One admin-gated configuration page holds four URL-addressable tabs — Raw objects (the default, §IV), Types (§V), Undo (§VI) and Merge review (§VII) — built on the standard configuration idioms: a page-level administrator gate (a non-administrator gets the standard configuration refusal, not a per-tab panel) and tab navigation addressable as ?tab=. The Merge review tab carries a nested detail route, /configuration/objects/merge-proposals/[proposalId].

One capability sits outside both surfaces. A targeted restore — reversing a single change-set the acting user is authorized for — is authorized per object, not by the administrator role, so it is neither a library view nor an admin tab: it has its own route, /restore/[changeSetId], reachable by any authorized user (§VI).

II. Library — the actor's artifacts

Claimed + plain rows · per-actor claims

Exactly the acting user's set. The library lists precisely the claimed and faceted artifacts resolved for the acting user — claims are resolved per actor against each installing extension's access grants, so two users on the same workspace can see different libraries. It never shows non-artifact internals; those live only in the object console's Raw objects tab (§IV). Rows are artifact identities, not raw object types.

Row anatomy. Each row is a title line over a muted meta line, hairline-divided, the last row dropping its divider. The title line carries a leading renderer glyph, the artifact name (bound to the effective identity's display name — never the raw object type), and a claimed-by chip. Two row species read at a glance: a claimed row, whose effective identity is a real installed extension, carries that extension's name in an indigo chip and opens through that extension's renderer — or, when that extension ships no renderer for the representation, through the generic fallback (§III); a plain row, a generic objects:object presenting as the default-artifact floor, carries a muted Default artifact chip and always opens through the generic fallback (§III). The meta line carries the owner / visibility and the relative updated time; the row's right edge holds the Open affordance.

Faceting & search. The Type facet filters the list by claiming extension or base type; the search field filters by name. An unfiltered library is grouped only by recency.

III. Renderer dispatch — how a row opens

Effective identity · type · MIME · fallback

Dispatch by effective identity. Opening a row resolves its renderer from the row's effective identity — the single value returned by the objects effective-identity service (a binding outranks a classic assertion, and any non-floor identity requires an installed extension). Three dispatch cases cover every row:

  • Typed-data artifact — a claimed email draft renders through its object type's registered renderer (the claiming extension's renderer).
  • File-form representation — an uploaded PDF keeps the MIME viewer handler for its representation.
  • Generic fallback — anything with no matching type renderer and no MIME handler (including a plain default-artifact row, or a claimed row whose extension ships no renderer for the representation) falls back to a read-only structured-data (JSON) view plus metadata. There is always a renderer; the fallback is never a blank.

Read authorization. Before any representation is served, the surface enforces raw-data read authorization (canonical object.* authorization plus surface gating). A row the viewer may list but not read opens to a not-authorized panel, never to its bytes.

Activation barrier. A claim-derived identity is library-visible for browsing as soon as the claim is active, but a row is not context-selectable or pinnable until its binding assertion lands. Until then the row shows a muted Preparing affordance where Pin / Add to context would sit, and Open still renders the row read-only.

IV. Raw objects — the object console's default tab

/configuration/objects · default tab · full objects table

Every row, unfiltered. Raw objects is the default tab of /configuration/objects — the former /data browse semantics, unchanged, now living under the admin console rather than as a mode of /artifacts. It lists every objects row, including the non-artifact internals that never become artifacts (send attempts, sender configuration, run bookkeeping). It is a dense table: object type (the raw type id), owner level / visibility (the canonical column model — user|team|organization|workspace × private|team|organization|public), source, canonical version, and updated. A wide table scrolls inside its own container.

Non-admins never reach the console. The gate is page-level: /configuration/objects requires an administrator session, so a non-administrator gets the standard configuration refusal for the whole page (not a per-tab panel) — no Raw-objects deep link bypasses it.

V. Types — the installed-type registry

/configuration/objects · read-only · installed types

Types exist only by installation. The Types tab is a read-only registry of every object type the workspace has installed. Each type is defined by exactly one installed kind:"artifact" extension; the registry lists each type, the extension that defines it, and the extensions that depend on it. There is no runtime type creation, and the tab decides nothing: no approval feed, no Promote/Archive, no Approved/Proposed pills, no per-type actions of any kind. It inventories what is installed; it never changes it.

One definer, declared dependents. The type model is a dependency model. Exactly one artifact extension defines a given type; any other extension that needs that type declares the defining extension as a dependency, so the type is guaranteed present wherever it is used. Because a type has a single definer, every row names one Defined by extension and there is nothing to reconcile between installs: two extensions that both define the same type is an install-time dependency conflict, resolved before install rather than at runtime. The Defined by value is that extension's manifest display name; the Used by value lists the extensions that declared that dependency.

The generic floor is defined too. The generic @cinatra-ai/objects:object type — the lossless floor every unclassifiable save lands on — is defined by the Default Artifact extension, which every workspace installs. It appears as an ordinary registry row: the floor exists because an installed extension defines it, exactly like every other type.

VI. Undo — data safety

/configuration/objects Undo tab · /restore/[changeSetId]

Two capabilities, authorized separately, on two surfaces. Undo is data safety, and it is two surfaces with two authorizations — the spec rules on each. (1) The Undo browser — the flat list of recent destructive object operations across the whole workspace — is the destructive-operations analogue of Raw objects (§IV): it inventories everyone's change-sets, so it is administrator-only and lives as the Undo tab of /configuration/objects, behind that page's administrator gate (§IV). (2) A targeted restore — reversing one specific change-set the acting user already holds a handle to — is authorized per affected object: an actor may restore a change-set when they hold restore authorization for every object it touched. That is the same per-object check the restore action enforces on confirm, and it is deliberately not the administrator role and carries no administrator bypass — so a non-administrator who is per-object-authorized for a change-set may restore that one change-set, and an administrator who is not per-object-authorized for some affected object is refused it. Because it is not administrator-gated, the targeted restore has its own dedicated route, /restore/[changeSetId] — not a tab of the admin console. This ruling blesses the shipped restore action's per-object authorization and corrects the post-consolidation gap where the only UI path to it had narrowed to administrators.

The admin browser (Undo tab). For an administrator the browser follows the design system's list-and-row idioms — each recent change-set a title line over a muted meta line, with a right-aligned Undo action that opens the restore confirmation for that change-set in place (an inline modal, unchanged from the former /data-safety surface); the empty state reads that there is nothing to undo. The confirm re-checks per-object authorization and applies the change-set's inverse. This in-console modal is the administrator's bulk-review path; the out-of-console entry points reach the same restore through the dedicated /restore/[changeSetId] route instead (below), never this cross-workspace browser.

Entry points render only when the actor can act. A targeted restore is reached from two entry affordances that live outside both surfaces — the in-chat post-mutation Undo last action chip beneath an agent-run card, and the Saved … · Undo toast on a successful mutation. Each deep-links to /restore/[changeSetId] for the addressed change-set (carrying the change-set id so that one restore surface opens directly). Each affordance renders only when the acting user is eligible to restore that change-set — per-object-authorized for every affected object, and the change-set still restorable. For a non-eligible user no affordance appears: no chip, no toast Undo action — the spec chooses suppression over a disabled control or an "ask an admin" state, because a transient safety affordance that cannot act is noise, and a rendered control must never dead-end on the not-authorized panel. The /restore/[changeSetId] route enforces the same eligibility server-side: it serves the single addressed change-set's restore surface for an authorized actor of any role, and refuses an unauthorized one with the standard not-authorized state — it never exposes the admin console's cross-workspace list to a non-administrator.

VII. Merge review — enrichment proposals

/configuration/objects Merge review tab · nested detail route · CAS-merge

Agents propose; a reviewer applies. Enrichment agents never write objects directly — they submit merge proposals: a set of proposed fields, each with its own provenance (a source, and where known a confidence), captured against a base version of the target object. Approving a proposal applies its fields over the object's current data through the canonical history-aware writer under the merge policy, using the captured base version as the optimistic-concurrency (CAS) expectation. This surface — the review feed and the per-proposal detail — is the human gate on that agent-proposed write. It formerly lived at /data-safety/merge-proposals; §VIII removes /data-safety, so it lands here as the Merge review tab of /configuration/objects, beside Raw objects (§IV), Types (§V) and Undo (§VI). A proposal's detail is a nested route, /configuration/objects/merge-proposals/[proposalId], and its back-link returns to the tab.

Why here, and not the notifications approvals feed. A merge proposal is a diff to review with apply-merge semantics — per-field values, provenance, a version-fenced apply — not a decide-once approval row. The retired /configuration/approvals inbox's successor, the unified /notifications surface, federates lightweight decide-once approvals read-time from the approval-source registry; it is not a home for a field-level review surface. So the review surface stays with the object-administration family under /configuration/objects, where route consolidation (§VIII) placed every object-admin surface. A notification that a proposal is awaiting review — deep-linking here — is a compatible future addition; that is notification, not relocation of the review.

Access — an administrator page with a per-object belt (consistent with §VI). The feed lists every pending proposal in the workspace, across all users — so, exactly like Raw objects (§IV) and the Undo browser (§VI), it is administrator-only: it lives behind the page-level administrator gate on /configuration/objects (§IV), so a non-administrator never reaches the tab or its nested detail route. Per-object authorization then rides beneath that admin gate as defense-in-depth: reading a proposal's proposed values additionally requires object.read on the target object, and Approve / Reject additionally require object.update on it, with no administrator bypass over that object check — an administrator who cannot themselves read or update the target object is refused the proposal. This layers §VI's per-object principle under the role gate rather than instead of it: unlike a targeted restore, a merge proposal has no per-actor entry point (it surfaces only through the admin feed), so the page keeps the administrator gate and the per-object check is the belt beneath it — the model is a conjunction (administrator and per-object-authorized), where §VI's targeted restore was per-object-only. Beneath that page gate, the per-proposal detail route addresses one opaque proposal id: an administrator who clears the page gate but lacks object.read on that proposal's target object gets the standard not-found — existence hidden at the record level — rather than a mode-level refusal, so naming a specific proposal never confirms to a reader who cannot see its object that the record exists.

States & affordances. The feed is a dense table of pending proposals only — proposal (id), object (id and type), source, base version and created — each row opening its detail; wide, it scrolls inside its own container, and its empty state reads exactly “No pending merge proposals.” A proposal detail shows the proposal status (Pending / Applied / Rejected), its target object, base version, source and proposing actor, and every proposed field with its value and per-field provenance. While a proposal is Pending the detail offers Approve and Reject; once decided, those actions retire. Approve applies the proposed fields over the object's current data with the captured base version as the CAS expectation — a concurrent write to the object since the proposal was submitted surfaces as a typed version conflict and returns the proposal to Pending for re-review; the applied merge is an ordinary reversible change-set, itself undoable through Undo (§VI). Reject marks the proposal rejected and changes no object data.

Version fence & reversibility

Approve writes through the canonical history-aware writer with the proposal's captured base version as the CAS expectation: if the object changed since the proposal was submitted the apply is refused as a typed version conflict and the proposal returns to Pending for re-review — an approval never silently overwrites a newer edit. Because the apply is a reversible internal change, an applied merge is an ordinary change-set on the Undo browser (§VI), reversible under the same per-object rules.

VIII. Route consolidation & retirement

/data* + /artifacts?mode= removed · no redirects

Three destinations, cleanly separated. The library serves every user at /artifacts; object administration lives on /configuration/objects as four tabs — Raw objects (§IV), Types (§V), Undo (§VI) and Merge review (§VII), plus the nested /configuration/objects/merge-proposals/[proposalId] detail route; targeted restore lives at /restore/[changeSetId] (§VI). Two families of route are removed: the former /data, /data/types and /data-safety browsers, and the old /artifacts?mode= admin modes (raw / types / undo / merge) together with the mode toggle itself — the review surface at /data-safety/merge-proposals was relocated (§VII), not dropped. Backward compatibility is out of scope: there are no redirects. A stale /data* link 404s; a legacy /artifacts?mode=… deep link simply falls through to the library — no crash, no refusal panel — because /artifacts now has only the one view.

No redirects

The old /data* routes are deleted outright — not redirected — and the /artifacts?mode= admin modes are gone. Any remaining link to /data, /data/types or /data-safety is a bug to fix at the link; a stray ?mode= query on /artifacts is ignored and the library renders.
