Cinatra — Application Design — Artifacts

/artifacts is the library — everything the acting user's agents and uploads have produced, each row opened by its type's renderer. Object change-set restore has its own page, /configuration/objects; a type's definitions and the objects stored under them live inside extension management, on the defining extension's detail view; and artifact change review lives on the shared artifact-review surface. Part of Cinatra Application Design; match it exactly.

Version 0.5.0

I. Two surfaces — the library and the restore console

/artifacts library · /configuration/objects restore

/artifacts is the library, and nothing else. It lists exactly the acting user's artifacts, for every user — there is no mode toggle and no Library button, because the library is the lone view. The page opens with the standard page header (title Artifacts, a one-line description, a closing etched rule), then a toolbar over the list. The sidebar entry is unchanged. Object administration is not a mode of this page.

/configuration/objects is the restore console — and nothing else. It is a single-purpose page that browses past object change sets (time-keyed, across every extension) and restores them (§IV). It is not a multi-tab object console: there is no raw-object browser tab, no type-registry tab, and no merge-review tab — the standalone object-administration console is dissolved. Two things that once lived on those tabs move to where they belong: a type's definitions and the objects stored under it fold into extension management, on the defining extension's detail view (§V); and artifact change review lives on the shared artifact-review surface (§VI). Because the page has one job, it carries no tablist.

A targeted restore has its own route. Reversing a single change set the acting user is authorized for is authorized per object, so it also has a dedicated route, /restore/[changeSetId], reachable by any authorized user (§IV).

II. Library — the actor's artifacts

Artifact rows · the acting user's set

Exactly the acting user's set. The library lists precisely the artifacts the acting user may see, resolved per actor against each defining extension's access grants, so two users on the same workspace can see different libraries. It never shows non-artifact internals. Rows are artifacts: each is an object of a defined type, presented by its display name — never a raw type id.

Row anatomy. Each row is a title line over a muted meta line, hairline-divided, the last row dropping its divider. The title line carries a leading renderer glyph, the artifact name (the artifact's display name), and a muted extension label naming the type's defining extension — the extension whose detail view holds that type's definition (§V). The row opens through that type's renderer, or, when the extension ships no renderer for the representation, through the generic fallback (§III). A file-form artifact (an upload) shows its MIME type in a mono label and opens through the MIME viewer. The meta line carries the owner / visibility and the relative updated time; the row's right edge holds the Open affordance.

Faceting & search. The Type facet filters the list by defining extension or type; the search field filters by name. An unfiltered library is grouped only by recency.

III. Renderer dispatch — how a row opens

Type renderer · MIME · fallback

Dispatch by type. Opening a row resolves its renderer from the artifact's type — the type its defining extension registered a renderer for. Three dispatch cases cover every row:

  • Typed-data artifact — an email draft renders through its type's registered renderer (the defining extension's renderer).
  • File-form representation — an uploaded PDF opens through the MIME viewer handler for its representation.
  • Generic fallback — anything whose type ships no renderer and has no MIME handler falls back to a read-only structured-data (JSON) view plus metadata. There is always a renderer; the fallback is never a blank.

Read authorization. Before any representation is served, the surface enforces raw-data read authorization (canonical object.* authorization plus surface gating). A row the viewer may list but not read opens to a not-authorized panel, never to its bytes.

IV. Restore console — undoing object change sets

/configuration/objects · change sets · /restore/[changeSetId]

What it restores. /configuration/objects is the restore console: it browses object change sets and undoes them, and it does nothing else. Every save, edit or delete an agent run — or a user action — makes over objects is captured as a reversible change set. The console lists them time-keyed, across every extension, and each entry says exactly what it would restore: the operation (what changed), the affected type, how many objects, and when. Restoring applies the change set's inverse through the canonical history-aware writer.

Authorized per object. A change set is restorable when the acting user holds restore authorization for every object it touched — the same per-object check the restore action enforces on confirm. There is no administrator bypass: an actor authorized for every affected object may restore it whatever their role, and an actor not authorized for some affected object is refused. The console lists the change sets the actor may act on; each row's right edge holds an Undo action that opens the restore confirmation in place (an inline modal), and the empty state reads that there is nothing to undo.

Entry points outside the console. Two affordances deep-link to a single change set's restore surface, /restore/[changeSetId]: the in-chat Undo last action chip beneath an agent-run card, and the Saved … · Undo toast on a successful mutation. Each renders only when the acting user is eligible to restore that change set — authorized for every affected object, and the change set still restorable. For a non-eligible user no affordance appears: no chip, no toast action — suppression over a disabled control, because a transient safety affordance that cannot act is noise, and a rendered control must never dead-end on the not-authorized panel. The /restore/[changeSetId] route enforces the same eligibility server-side: it serves the addressed change set's restore surface for an authorized actor of any role and refuses an unauthorized one with the standard not-authorized state.

V. Type definitions & stored objects — in extension management

Extension detail view · Defined by / Used by · read-only

No standalone type registry. A type exists only because an installed artifact extension defines it, so its definition — and the objects stored under it — belong to that extension's detail view in extension management (see Application Design — Extensions), not to a separate console. Grouping is by the defining extension, never by whoever created a given object: a consumer extension may create objects of a depended-on type, but the type and its stored objects are shown under the extension that defines the type.

The dependency model — Defined by / Used by. Exactly one artifact extension defines a type; any extension that needs it declares the defining extension as a dependency, so the type is guaranteed present wherever it is used. Each type therefore names one Defined by extension (its manifest display name), and its Used by lists the extensions that declared that dependency. Two extensions defining the same type is an install-time dependency conflict, resolved before install — never reconciled at runtime.

What the detail view shows. On an artifact extension's detail view, the artifact domain contributes two read-only panels: a Defines table — each type this extension defines, with a schema summary and its Used by dependents; and a Stored objects panel — the objects stored under those types, for record inspection. It is an inventory: it decides nothing — no approval feed, no Promote/Archive, no pills, no per-type actions.

Every stored object has a defining extension

There is no untyped floor and no default catch-all extension: every object stored is an object of a type some installed artifact extension defines, and dependents guarantee that type is present at install time (an extension that needs a type declares its definer as a dependency). Record inspection therefore always resolves an object to the extension that defines its type — which is exactly where its Stored objects panel lives.

VI. Change review — on the artifact-review surface

Shared review surface · cinatra-ai/cinatra#1795

One review surface, not a console tab. Agent-proposed changes to artifacts — enrichment field merges and the like — are reviewed on the shared, generic artifact-review surface, not on the restore console and not on a tab of it. That surface (immutable review targets, gate-provenance authorization, and the host decision chrome) is specified separately in cinatra-ai/cinatra#1795; this spec references it and adds no review tab here. A notification that a change awaits review deep-links to that surface — decide-once review lands in /notifications (see Application Design — Notifications), which federates pending approvals; a field-level artifact review opens on the artifact-review surface itself.

Why it folds out

A change proposal is a diff to review over an immutable target, exactly the shape the generic artifact-review surface already handles — so every human decision over an artifact, whatever produced the proposal, is reviewed in one place rather than duplicated as an object-admin tab. This spec owns the library, the renderer, the restore console and the extension-management fold; the review surface is cinatra-ai/cinatra#1795. An applied change is an ordinary reversible change set, undoable through the restore console (§IV).

VII. Route consolidation & retirement

standalone object console dissolved · no redirects

Where each concern lives now. The library serves every user at /artifacts (no mode toggle). /configuration/objects is the restore console and nothing else — object change sets, browsed and undone (§IV) — with targeted restore at /restore/[changeSetId]. A type's definitions and stored objects live on the defining extension's detail view in extension management (§V); change review lives on the shared artifact-review surface, cinatra-ai/cinatra#1795 (§VI). What is removed: the standalone object-administration console is dissolved — there is no four-tab /configuration/objects (no Raw objects tab, no standalone Types registry, no Merge review tab) and no /configuration/objects/merge-proposals/[proposalId] detail route; the former /data, /data/types and /data-safety browsers are gone; and the old /artifacts?mode= admin modes and the mode toggle are gone. Backward compatibility is out of scope: there are no redirects. A stale /data* link 404s; a legacy /artifacts?mode=… deep link simply falls through to the library — no crash, no refusal panel — because /artifacts now has only the one view.

No redirects

The dissolved console's tabs are not redirected anywhere — record inspection is reached through extension management (§V) and change review through cinatra-ai/cinatra#1795 (§VI). The old /data* routes are deleted outright; any remaining link to /data, /data/types or /data-safety is a bug to fix at the link, and a stray ?mode= query on /artifacts is ignored while the library renders.
